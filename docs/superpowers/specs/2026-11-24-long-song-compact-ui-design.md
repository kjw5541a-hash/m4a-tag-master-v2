# 긴 곡 바로 저장 · 빌드 번호 위치 · 편집 화면 한 화면에 — 짧은 설계

## 의도

사용자 요청(2026-11-24) 세 가지:
1. 15분 넘는 곡은 분석을 건너뛰고 바로 '저장 필요'가 되게. 대신 커버 이미지는 무작위로 찾아 준다.
2. 큐 화면의 빌드 날짜·번호가 [파일 추가] 바로 밑에 붙어 있어 어색하다. 화면 맨 아래로.
3. 곡 편집 화면이 한 화면에 다 안 보이고 항목 구분이 잘 안 된다. 줄 간격을 줄이고, 구분선을 넣고, 한 화면에 보이게.

## 목표 / 비목표

- 목표: 15분 넘는 곡은 iTunes·가사 검색을 자동으로 하지 않고, 무작위 사진(picsum.photos, 노래와 무관 — 사용자 확인) 하나를 받아 커버로 넣은 뒤 바로 '분석 건너뜀, 저장 필요'.
- 목표: 그런 곡의 편집 화면에 [다른 이미지] — 누르면 무작위 사진을 다시 받는다.
- 목표: 큐의 빌드 표시는 곡이 적어도 화면 맨 아래에 붙는다.
- 목표: 편집 화면은 아이폰 16 Pro 홈 화면 앱(852pt, 위 안전 영역 59·아래 34)에서 저장 바 위로 분석 칸까지 스크롤 없이 보인다. 묶음(커버·검색·후보 / 제목·가수·앨범 / 가사 / 분석) 사이에 구분선.
- 비목표: 짧은 곡의 동작, 직접 검색(검색어+🔍)·후보 고르기(긴 곡도 그대로 쓸 수 있다), 터치 영역 44pt 줄이기.
- 피할 것: 무작위 사진을 받는 동안 저장되어 화면과 파일이 다른 것(받는 동안은 '검색 중'처럼 잠근다), 무작위 사진 요청에 곡 정보를 싣는 것.

## 방식

| 방식 | 장단점 |
|---|---|
| **A. 큐에 넣을 때 긴 곡은 lookup 대신 무작위 커버만 받고 review (선택)** | 검색을 기다리지 않는다. 사진 받는 1초 안팎만 잠긴다 |
| B. 검색은 그대로 하고 분석만 건너뜀(지금) | 긴 곡(대부분 모음·라이브)은 검색이 맞지 않아 시간만 든다 — 요청과 다름 |
| C. 노래 제목으로 찾은 커버 중 무작위 | 사용자가 '노래와 무관한 무작위 사진'이 맞다고 확인 |

## 정한 것

- **판단 기준:** 컨테이너 길이 `duration > MAX_ANALYSIS_SEC`(15분). 파일에 분석이 이미 있으면 분석 상태는 지금처럼 'done'(태그 값 유지), 검색만 건너뛴다.
- **무작위 커버:** 스토어 액션 `shuffleCover(id)` — lookup과 같은 요청 번호(begin)를 쓰고, 받는 동안 status 'searching', 끝나면 'review'. URL `https://picsum.photos/1000?random=<난수>`(iTunes 커버와 같은 1000px 정사각, CORS 허용 확인). 실패하면 커버는 원래대로 두고 오류 표시 없이 review.
- **[다른 이미지]:** 편집 화면 커버 버튼들 옆, 긴 곡에만.
- **큐:** 앱 바깥 상자를 세로 flex로, 큐 화면이 남은 높이를 채우고 빌드 표시는 `mt-auto`.
- **편집 화면:** 묶음 사이 구분선, 간격 16→8px 안팎. 커버 96px에 커버 버튼을 옆으로. [가수⇄제목]은 앨범 줄로. 가사 줄은 한 줄. 분석 칸은 테두리 상자를 없애고 제목 줄에 BPM 입력·×2·÷2, 조성 줄 끝에 [다시 분석], 주요 진행은 작은 글씨.

## 빌더에게 맡긴 것

- 정확한 여백·글자 크기. 확인은 WebKit 393×787 뷰(안전 영역을 뺀 높이)에서 분석 칸 끝이 저장 바 위에 오는지 잰다.
