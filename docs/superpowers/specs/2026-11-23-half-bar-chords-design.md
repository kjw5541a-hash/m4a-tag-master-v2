# 코드를 반 마디 단위로 — 짧은 설계

## 의도

비트(박)마다 코드를 정해서 곡이 너무 잘게 쪼개졌다(참고곡 3:49에 292구간, 중앙값 0.46초). 사용자 요청: "노래 BPM을 먼저 확인하고, 그걸 기준으로 반마디 단위로 코드를 분석". 화면에서 코드 진행을 읽을 수 있게 하는 것이 목적이다.

## 목표 / 비목표

- 목표: BPM을 먼저 정하고(배속 보정), 그 BPM의 2박(반 마디)마다 코드 하나. 사용자가 BPM을 ×2·÷2·입력으로 고치면 코드도 그 BPM 기준으로 다시 묶는다.
- 목표: 주변 조성에 맞는 코드를 조금 우선한다(전조가 있는 곡도 구간마다 따로).
- 비목표: 7화음·분수 코드(결정 #5: 3화음 참고용), 마디 첫 박 검출, 스키마 변경.
- 피할 것: 화면에서 코드가 여전히 1초 미만으로 쪼개지는 것, 뚜렷한 코드를 조성 가산점이 덮어쓰는 것.

## 근거 데이터 (참고곡 '180도', 2026-11-23)

- 검출 BPM 134.9, 참고표 68 → 발라드가 두 배로 잡힌다. 김동률 '산책'도 132.2(발라드), 이적 '하늘을 달리다'는 117.7.
- 20초 구간별 음계 맞춤: 0~20초 D장조, 20~200초 D♭·A♭ 계열, 200초~ E♭·A♭ 계열. 곡 전체 조성 하나로는 가산점을 줄 수 없다.

## 방식

| 방식 | 장단점 |
|---|---|
| A. 검출 BPM 그대로, 120 기준으로 묶음 수만 바꿈 | 화면 BPM과 묶음 기준이 따로 논다. 사용자가 BPM을 고쳐도 코드는 그대로 |
| **B. BPM을 먼저 정하고(120 이상이면 ÷2) 그 BPM으로 묶음, BPM을 고치면 다시 묶음 (선택)** | 사용자 요청 그대로. 박 사이 크로마를 메모리에 들고 있어야 한다(곡당 수십 KB) |
| C. 사용자가 BPM을 확인한 뒤에만 코드 분석 | 자동 분석 흐름(큐에서 모두 저장)과 맞지 않는다 |

## 정한 것

- **BPM:** 검출 BPM이 120 이상이면 반으로 해서 저장·표시한다(180도 67.5, 산책 66.1, 하늘을 달리다 117.7 그대로). 빠른 곡이 반으로 나오면 사용자가 ×2를 누른다.
- **반 마디:** BPM의 2박. 검출 비트 몇 개를 한 묶음으로 할지 = `max(1, round(2 × 검출BPM / BPM))`.
- **묶음 시작점:** 첫 박을 모르므로 가능한 시작 위치(묶음 크기만큼)를 모두 해 보고, 묶음마다 가장 잘 맞는 코드 점수의 합이 가장 큰 쪽을 쓴다.
- **코드 고르기:** 묶음 안 HPCP 프레임 평균(12음)과 장·단 3화음 24개 틀의 코사인 유사도. 앞뒤 약 ±8묶음의 음 분포로 그 구간에 가장 맞는 장음계를 고르고, 그 음계의 3화음(I ii iii IV V vi)에 가산점(×1.1). 소리가 거의 없거나 유사도가 기준 미만이면 N.
- **후처리:** 같은 코드가 이어지면 합친다. 1박 흡수 규칙은 없앤다(묶음이 이미 그 역할).
- **BPM 수정:** 분석할 때 비트 사이 크로마를 곡 항목(메모리)에 둔다. ×2·÷2·입력으로 BPM이 바뀌면 그것으로 다시 묶어 chords·topProgressions를 바꾼다. 파일에서 읽은 분석(크로마 없음)은 BPM만 바뀐다.
- **스키마:** 그대로. analyzer를 `m4a-tag-master@3`으로.
