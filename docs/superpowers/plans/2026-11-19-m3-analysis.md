# M3 화성 분석 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 곡을 넣으면 기기 안에서 BPM·조성·비트 단위 코드를 분석해 편집 화면에 보여 주고, 고칠 수 있게 하고, 저장할 때 `----:com.jw.mapp:ANALYSIS`(스키마 v1)로 파일에 넣는다. 정확도를 잴 평가 스크립트도 만든다. 사용자 피드백(가사가 바뀌었는지 앱에서 안 보임)도 함께 고친다.

**Architecture:** M0에서 만든 essentia 파이프라인(`src/analysis.ts`, `src/analyzer.worker.ts`)을 그대로 쓰고, 코드 후처리·`topProgressions`·스키마는 순수 함수로 분리해 Node에서 테스트한다. 브라우저 실행기(`src/runAnalysis.ts`)가 디코드 → 모노 → 곡마다 새 워커 → 결과를 스키마로 만든다. 스토어가 분석을 곡 단위로 차례로 돌리고(동시에 하나), 화면은 분석 카드(`src/ui/AnalysisCard.tsx`)로 보여 준다.

**Tech Stack:** 기존 그대로(Vite 8, React 19, TypeScript, zustand 5, essentia.js 0.1.3, node:test, Playwright e2e). 새 의존성 없음.

**Spec:** `~/Downloads/m4a_tag_master_v2_기획서.md` — M3 범위는 5.1(기존 ANALYSIS면 건너뜀), 5.5, 6.2의 분석 카드, 7.2·7.3, 9장의 분석 관련 행, 11.2, 12장 M3 행.

## Global Constraints

- 오디오는 기기 밖으로 나가지 않는다. 분석은 모두 브라우저(워커) 안에서.
- 분석 파이프라인 값은 M0에서 정한 것 그대로: 44.1kHz 모노, `RhythmExtractor2013(signal, 208, 'multifeature', 40)`, `KeyExtractor` 기본값, 프레임 4096 / hop 2048, `ChordsDetectionBeats(…, 'interbeat_median', 2048, 44100)`.
- 분석 길이 상한 15분(`MAX_ANALYSIS_SEC = 15 * 60`). 넘으면 분석만 건너뛰고 태깅은 된다.
- 한 번에 한 곡만 분석한다. 곡마다 워커를 새로 만들고 끝나면 `terminate()`.
- 워커에서 60초 동안 아무 메시지가 없으면 실패로 보고 워커를 종료한다.
- 스키마는 기획서 7.2 그대로: `version: 1`, `analyzer`, `analyzedAt`(ISO 8601), `duration`(초, 소수 둘째 자리), `bpm`(소수 첫째 자리), `bpmConfidence`(소수 둘째 자리), `key`, `scale`, `keyStrength`(소수 둘째 자리), `edited`, `topProgressions: { chords: string[]; count: number }[]`(최대 3개), `chords: { start; end; chord }[]`(시간 순, 빈틈 없음, 소수 둘째 자리).
- `key`는 `C C# D D# E F F# G G# A A# B` 중 하나, `scale`은 `major | minor`. 코드 표기는 이 12개 + 단조면 `m`, 코드 없음은 `N`.
- `analyzer` 값: `'m4a-tag-master@2 essentia.js@0.1.3'`.
- 화면 문구(그대로): 카드 제목 `분석 (참고용)`, 15분 초과 `분석은 15분 이하 곡만 할 수 있어요. 태그는 저장할 수 있어요`, 디코드 실패 `오디오를 해석하지 못해 분석을 건너뜁니다`, 워커 실패·응답 없음 `분석 중 메모리가 부족했어요`, 다시 분석 확인 `수정한 값이 덮어써져요. 다시 분석할까요?`.
- 파일에 이미 유효한 v1 ANALYSIS가 있으면 자동 분석하지 않는다. v1이 아니거나 형식이 틀린 ANALYSIS는 그 원문을 저장 때 그대로 둔다(덮어쓰지 않음).
- UI 문구·코드 주석 한국어, 입력 글꼴 16px 이상, 터치 영역 44px 이상.
- 테스트는 `node:test`, 상대 import에 `.ts`. iTunes를 부르는 스토어 테스트는 파일당 분당 20회 리미터를 공유하므로, 분석 스토어 테스트는 **새 파일** `src/store-analysis.test.ts`에 둔다.
- 새 의존성 금지. `git add -A` 금지.

## Review Focus

- 아이폰에서 워커가 메모리 부족으로 죽거나 응답이 없으면 → 카드가 '분석 중'에 멈추지 않고 실패 문구가 나오며 저장할 수 있어야 한다 (Task 3 워치독, Task 4 테스트 3).
- 분석 중에 곡을 큐에서 지우면 → 되살아나지 않고 다음 곡 분석이 이어진다 (Task 4 테스트 4).
- v2로 분석까지 저장한 파일을 다시 열면 → 다시 분석하지 않고, 사용자가 고친 BPM(`edited: true`)이 그대로 남고, 다시 저장해도 값이 바뀌지 않는다 (Task 4 테스트 5).
- BPM을 고친 뒤 [다시 분석]을 누르면 → 확인을 묻고, 확인했을 때만 덮어쓴다 (Task 5).
- 15분 넘는 곡 → 분석 건너뜀 문구, 저장 가능 (Task 4 테스트 6).

## Rulings (기획서와 다르게, 또는 기획서가 정하지 않은 것)

- 분석은 파일을 추가하면 자동으로 시작한다(기획서 3장 S1). 검색과 동시에 돌고, 곡끼리는 차례로 돈다. 자동 분석 끄기 설정(F9, P1)은 만들지 않는다.
- 분석이 끝날 때까지 [저장 · 공유]를 막는다('분석 기다리는 중…'). 실측 1분당 약 1.2초라 기다릴 만하고, 분석이 빠진 파일이 저장되는 것보다 낫다. 분석이 실패·건너뜀이면 저장할 수 있다. 분석 취소 버튼은 만들지 않는다.
- 분석 미리듣기(F5의 P1)는 만들지 않는다.
- 코드 후처리 초기값: 강도 0.3 미만은 `N`. 근거: 샘플 2곡의 비트별 강도는 -1~1, 하위 10%가 0.40~0.53, -1은 소리가 거의 없는 구간. 1비트짜리 A-B-A 흔들림은 비트의 약 10%. 값은 Task 6 평가로 조정한다.
- 사용자 피드백 반영: 가사 시트 맨 위에 지금 들어 있는 가사를 보여 주고, 편집 화면의 가사 행에 첫 줄을 보여 준다(Task 1).

### Task 3: 브라우저 분석 실행기 (기획서 5.5 1~2·9단계, 9장)

**Files:** Create: `src/runAnalysis.ts`

**Interfaces:**
- Consumes: `SAMPLE_RATE`, `toAnalysis`, `AnalysisResult` (Task 2), 워커 메시지 규약(`src/analyzer.worker.ts`: `ready` → 신호 받음 → `progress`/`done`/`error`)
- Produces:
  - `export const MAX_ANALYSIS_SEC = 15 * 60`
  - `export class AnalysisError extends Error {}` — 메시지는 화면에 그대로
  - `export async function runAnalysis(bytes: Uint8Array, onProgress: (ratio: number) => void): Promise<MappAnalysisV1>`
    - `new OfflineAudioContext(1, 1, SAMPLE_RATE).decodeAudioData(bytes.slice().buffer)`(원본을 떼어 가지 않게 복사본) → 실패하면 `AnalysisError('오디오를 해석하지 못해 분석을 건너뜁니다')`
    - 디코드 길이가 `MAX_ANALYSIS_SEC`를 넘으면 `AnalysisError('분석은 15분 이하 곡만 할 수 있어요. 태그는 저장할 수 있어요')`
    - 채널 평균으로 모노 `Float32Array`를 만들고 `AudioBuffer` 참조는 버린다.
    - 워커를 새로 만들고(`new Worker(new URL('./analyzer.worker.ts', import.meta.url), { type: 'module' })`), `ready`를 받으면 `{ signal, method: 'multifeature' }`를 transfer로 넘긴다.
    - `progress`의 단계를 0~1 하나로 묶어 `onProgress`에 넘긴다(리듬 0~0.5, 조성 0.5~0.55, HPCP 0.55~0.95, 코드 0.95~1).
    - 60초 동안 메시지가 없거나 `onerror`·`error`면 워커를 끝내고 `AnalysisError('분석 중 메모리가 부족했어요')`.
    - `done`이면 워커를 끝내고 `toAnalysis(result, 디코드 길이, new Date().toISOString())`.
    - 어떤 경로로 끝나든 워커는 반드시 `terminate()`.
- 브라우저 전용이라 이 Task에서는 단위 테스트를 하지 않는다. Task 5의 e2e가 실제 Chrome에서 끝까지 돌린다.
